2. The Read Path (Browser to Row)

A warm dashboard load costs zero database operations. Cache is checked only after strict authorization and scope narrowing. The initial WidgetHost request acts as the trigger for both reads and targeted refreshes.

3. Authorization & Scope Narrowing (Security Path)

Crucial security path demonstrating that `core-api` remains the sole authority on identity. The user's token is never substituted for an M2M token.

sequenceDiagram autonumber participant B as core-app (Browser) participant C as core-api participant D as dashboard-service participant M as Memcached B->>C: Batch Request (Authenticated Session) Note over C,D: Forwards the user's OWN bearer token.
Never an M2M token. C->>D: Proxy Request D->>D: Decode token to read client_id (Resolve Tenant) D->>C: POST /user/introspect-permissions
(M2M-authenticated, x-tenant-client-id) C->>C: Validate token & resolve permissions C-->>D: Return User + Permission Set D->>D: Reject if introspected clientId ≠ token clientId D->>D: Check calculator's requiredPermission D->>D: Narrow requested scope to what viewer may see D->>M: Cache Lookup using Narrowed Scope Key

4. Compute, Scheduling, & Delivery

Showing how both scheduled placements and manual user refreshes drive computation. The Dispatch Consumer acts as a "fan-out" mechanism, converting a single time-based tick into targeted jobs for only the active widget placements.
